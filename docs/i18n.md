# Internationalization (I18n) Guide

Every string PermissionForge shows — the admin screens, their flash messages, the validation messages of its models,
the JSON API's error messages, the audit log's sentences and the CSV headers — comes from a key under
`permission_forge:` in the gem's own locale files, or is data your application stored (a name, an email, a column
name). The gem reads no Rails-core key (`errors.messages.*`, `support.array`, `datetime.distance_in_words`, …) and
never falls back to Rails' English inflections (`humanize`, `pluralize`, `to_sentence`): the test suite runs without
`rails-i18n` and renders every screen, error state, export and API error under a pseudo-locale to prove it
(`test/permission_forge/html/locale_leak_test.rb`). You do not need `rails-i18n` for the admin to read fully in Albanian
or Macedonian.

## Supported Languages

| Locale | Language | File |
|--------|----------|------|
| `en` | English | `config/locales/permission_forge.en.yml` |
| `sq` | Shqip | `config/locales/permission_forge.sq.yml` |
| `mk` | Makedonski | `config/locales/permission_forge.mk.yml` |

## How It Works

### Admin UI

The admin UI includes a locale switcher in the sidebar. Clicking a language sets the locale in the session, so it persists across page loads. You can also pass `?locale=sq` as a query parameter.

Switcher links carry only the current path plus the validated `locale` param — other query parameters are not preserved (this prevents reflected-parameter tricks from turning the switcher into an off-site link).

The locale is resolved in this order:
1. `params[:locale]` (if valid)
2. `session[:permission_forge_locale]` (persisted from previous switch)
3. `I18n.default_locale` (fallback)

### JSON API

The API accepts locale via:
1. `locale` query/body parameter (highest priority)
2. `Accept-Language` HTTP header
3. `I18n.default_locale` (fallback)

```bash fragment
# Via query parameter
curl /permission_forge/api/permission_sets?locale=sq

# Via Accept-Language header
curl -H "Accept-Language: sq" /permission_forge/api/permission_sets
```

`Accept-Language` parsing accepts bare tags (`en`), region forms (`en-US`), and lists with q-weights (`en-US;q=0.8,sq`) — each tag is reduced to its primary language subtag. **q-values are ignored**: the first tag, in the order the header lists them, whose primary subtag is an available locale wins (`en;q=0.1, sq` gives `en`). A `locale` parameter that is not an available locale is not combined with the header: the request falls back to `I18n.default_locale`. The locale is reset on every request (falling back to `I18n.default_locale` when none matches), so one request's locale never leaks into the next.

Every message of a 4xx envelope (`error.messages`) is translated the same way: a validation message of the gem's
models, a refused filter of `GET /api/audit_events`, an unreadable body, a missing section. The 401 of an
unconfigured `api_auth` has no body.

### Configuration

```ruby fragment
PermissionForge.configure do |config|
  # Limit which locales are loaded.
  # nil (default) falls back to PermissionForge::BUNDLED_LOCALES ([:en, :sq, :mk])
  config.available_locales = [:en, :sq, :mk]
end
```

Only matching locale files are loaded. When `available_locales` is unset, the gem falls back to `PermissionForge::BUNDLED_LOCALES` — the locales it ships translations for (`[:en, :sq, :mk]`) — so the admin UI never offers host-app locales (e.g., ones added by Faker) that the gem can't translate.

## Overriding Translations

Host app locale files load after engine locale files, so you can override any key by defining it in your own locale file:

```yaml
# config/locales/permission_forge_overrides.en.yml
en:
  permission_forge:
    nav:
      permission_sets: "Roles"
    flash:
      permission_sets:
        created: "New permission set saved!"
```

## Your Models and Columns in the Admin

The admin names *your* models, columns, associations and actions everywhere: "Only show **Customers** where **Owner**
is the current user", the field list of a Resource, the rule builder's selects, a person's effective access. These are
your application's names, and the gem does not translate them. What it shows, in this order:

1. **Your translation**, when your application has one — the standard Rails keys, in the language of the page:

   ```yaml
   # config/locales/sq.yml (in your host app)
   sq:
     activerecord:
       models:
         customer:
           one: Klienti
           other: Klientët
       attributes:
         customer:
           full_address: Adresa e plotë
           owner: Pronari          # an association is named like an attribute
   ```

   Translate `activerecord.models.<model>` (with `one` and `other`: the plural is used in sentences) and
   `activerecord.attributes.<model>.<column or association>` for every locale you offer the admin in.
2. **The label stored on the row** — a Resource's label, a field's label, an action's label — when the admin or the API
   set one (a field row generated from a column is labelled with the column's name made readable, in English, at the
   time it is generated; an admin can change it).
3. **The name as stored**, verbatim, drawn as code (`full_address`, `Billing::Invoice`, `export_csv`) — never an English
   "Full address" or "Customers" made up by inflection. Without a translation of the model's plural, sentences read
   "Only show **Customer records** where …" (`permission_forge.ui.resource_plural`).

The one definition of each of these is `PermissionForge::Admin::FieldLabel`, `Admin::ModelLabel` and
`Admin::ActionLabel`; the gem's own translations are never consulted for a host name, and Rails' `human_attribute_name`
fallback (the humanized English name) is not treated as a translation.

The gem's own models (`PermissionForge::PermissionSet`, …) are labelled by the gem: a validation message names its
attribute from `permission_forge.validations.attributes.*`, never from `activerecord.attributes.permission_forge/…`.

## Column Defaults Are English

The install migration gives the string columns of the gem's tables English defaults so that a row written outside the
admin (a console, a script, an older version) is never nameless: `'Untitled Permission Set'`, `'Untitled Field'`,
`'Untitled Rule'`, and the rule's `failure_message` default `'You do not have permission to perform this action.'`.
These defaults are data, not translations:

- the admin never pre-fills a form with one — a new rule's name and blocked message start blank, whatever the language
  (`Admin::Prefill`; a test enumerates every string column default of the nine tables against every new-record screen);
- a rule whose `failure_message` is blank denies with the gem's own sentence in the current locale
  (`permission_forge.denials.rule_default`, through `NotAuthorizedError#failure_messages`), so an admin who writes
  nothing gets a translated denial, not English;
- a rule that already holds the English default (created through the API, a script, or the admin of 0.14) keeps it
  until someone edits it. To let such rules fall back to the translated sentence, blank the stored text:

  ```ruby fragment
  PermissionForge::PermissionSetRule
    .where(failure_message: 'You do not have permission to perform this action.')
    .find_each { |rule| rule.update!(failure_message: '') }   # each change is audited (rule.updated)
  ```

## Adding a New Language

### Step 1: Create the Locale File

Copy the English reference file:

```bash fragment
cp config/locales/permission_forge.en.yml config/locales/permission_forge.XX.yml
```

### Step 2: Update the Top-Level Key

Change `en:` to your locale code (e.g., `pt:` for Portuguese).

### Step 3: Translate All Values

Translate every string value. Keep these unchanged:
- Interpolation variables: `%{count}`, `%{name}`, `%{time}`, `%{id}`, `%{error}`, `%{resource}`
- HTML markup in `_html` suffix keys (e.g., `<code class="pf-mono">current_user</code>`)
- Brand name: "PermissionForge"
- Technical abbreviations: "UUID", "CRUD", "R", "C", "E", "D"
- Code tokens: `current_user`, `example.com`, `company.organization`
- The UI names, verbatim: Permission Set, Muting Permission Set, Permission Set Group, Resource

Two lints in the test suite keep a translation honest (`test/permission_forge/i18n_test.rb`):

- **No English left behind.** A value identical to the English one, when the English value is prose (three Latin
  letters outside its placeholders, one of them lower-case), fails unless
  `test/permission_forge/i18n_identical_allowlist.yml` lists the key with a reason — a word the language shares
  ("person" in Albanian), the brand, a sample value. A format of placeholders (`%{who} · %{when}`) or an acronym
  (`API`, `UUID`) needs no entry.
- **One pair of quotation marks per locale.** Each file quotes one way (`en` and `sq` “…”, `mk` „…“); the lint names
  every line with another typographic quotation mark. Add your locale's pair to `I18nTest::QUOTES`.

### Step 4: Verify with i18n-tasks

```bash fragment
bundle exec i18n-tasks missing
bundle exec i18n-tasks unused
```

### Step 5: Register the Locale

Update `ApplicationHelper::LOCALE_LABELS` in `app/helpers/permission_forge/application_helper.rb`:

```ruby fragment
LOCALE_LABELS = {
  en: 'English',
  sq: 'Shqip',
  mk: 'Makedonski',
  # ... add your locale:
  pt: 'Portugues',
}.freeze
```

Also add the locale to `PermissionForge::BUNDLED_LOCALES` in `lib/permission_forge.rb`. The engine only loads locale files whose locale appears in `config.available_locales` (or, when unset, `BUNDLED_LOCALES`) — an unregistered file is never loaded.

### Step 6: Submit a PR

Community translations are welcome! Please ensure:
- All keys match the English reference file (no missing or extra keys)
- Interpolation variables are preserved
- Pluralization forms (`one`/`other`) are grammatically correct
- `_html` suffix keys preserve HTML markup

## Key Reference

All keys live under the `permission_forge:` namespace:

| Namespace | Purpose | Example Key |
|-----------|---------|-------------|
| `ui` | Shared admin vocabulary: levels, states, operators, badges, dates, change descriptions, the plural of a host model (`resource_plural`), the audit CSV header (`audit.csv`) | `permission_forge.ui.levels.masked` |
| `nav` | Sidebar navigation | `permission_forge.nav.permission_sets` |
| `shared` | Shared partials (frames, cells, savebar, expiry picker, audit footer) | `permission_forge.shared.savebar.review` |
| `home`, `people`, `assignments`, `bulk_assignments` | Home and people screens | `permission_forge.people.show.tabs.effective` |
| `permission_sets`, `resources`, `resource_fields`, `resource_actions`, `permission_set_rules` | Permission Set editor, resource page, field drawer, actions, rule builder | `permission_forge.permission_set_rules.builder.preview` |
| `permission_set_groups`, `field_lookups` | Groups and Field lookup | `permission_forge.field_lookups.show.who_can_see` |
| `settings` | Read-only Settings page; `settings.items.<key>.name/desc` for every option | `permission_forge.settings.items.cache_ttl.name` |
| `flash` | Toast messages | `permission_forge.flash.assignments.assigned` |
| `errors.admin` | Admin form validation messages | `permission_forge.errors.admin.ip` |
| `api.errors` | API error messages | `permission_forge.api.errors.not_found` |
| `denials` | What a row-level rule says when it denies and has no message of its own | `permission_forge.denials.rule_default` |
| `layouts` | Page title | `permission_forge.layouts.application.title` |
| `validations` | Every validation message of the gem's models (`blank`, `taken`, `too_long`, `requires`, per-model keys), the attribute names used in a sentence (`attributes.*`) and the sentence format (`full_message`) | `permission_forge.validations.resource.invalid_name` |

Dates in the admin use the engine's own month names (`ui.months.*`) and relative words (`ui.dates.*`); the host app does not need `rails-i18n`.

## Translation Quality Disclaimer

Built-in translations (sq, mk) are provided as a convenience. **We do not guarantee the accuracy of non-English translations.** If you find an error, please submit a PR with the correction.

## Development: i18n-tasks

The gem ships with an `i18n-tasks` configuration at `config/i18n-tasks.yml`. Use it to verify translation health:

```bash fragment
# Full health check
bundle exec i18n-tasks health

# Find missing translations
bundle exec i18n-tasks missing

# Find unused translations
bundle exec i18n-tasks unused

# Normalize locale files (consistent key ordering)
bundle exec i18n-tasks normalize
```

Add `bundle exec i18n-tasks health` to your CI pipeline to catch missing translations early.

`i18n-tasks` depends on `rails-i18n`, so the gem is installed in development; the test process never loads it
(`test/test_helper.rb` refuses to start if it is on the load path), and nothing in the gem requires it.
